# Aceitação — M31, eixo de API

Valida a entrega do `theo-skills 0.3.0` (tag `v0.12.0`). **Não** valida o milestone inteiro: dos
seis critérios da DoD do M31, três são de tela e dependem do plano 2, no `theo-cloud`.

## Critério 1 — a listagem distingue publicada de achável

**Alvo: `app-dev.usetheo.dev`, serviço no ar.** Exercitado pela sessão real do dashboard
(`GET /v1/dashboard/skills?limit=100` → `200`), lendo a resposta que o app de fato recebeu.

```
lt020-1785621219            visibility: private   embedded: false
m26-verify-clique           visibility: private   embedded: true
redteam-cambio-1785615135   visibility: private   embedded: false
```

**Status: `passed`.** Os dois campos chegam, e o `embedded` **discrimina** — não é constante.

**O que a medição revelou, e não era o objetivo:** **2 das 3 skills do workspace de dev estão
publicadas e invisíveis à busca semântica**, incluindo a `redteam-cambio`, que é a mais próxima
de uma skill real do acervo. Antes desta entrega não havia como saber disso por nenhuma
superfície — o painel as mostrava idênticas a uma indexada. O campo cumpriu seu propósito na
primeira leitura.

## Critério 2 — a busca diz de qual perna veio cada resultado

**Alvo: build da tag `v0.12.0`** em worktree limpo (`git worktree add /tmp/acc-m31 v0.12.0`,
`pnpm install --frozen-lockfile`, `pnpm -r build`), servido contra o Postgres do projeto.
`git describe --tags --exact-match HEAD` → `v0.12.0`.

Duas skills reais publicadas pela API. Consulta: *"converter dinheiro estrangeiro"*.

```
cambio-real       score=0.03306   matched=[{leg:vector, rank:2}, {leg:keyword, rank:1}]
triagem-chamado   score=0.01667   matched=[{leg:vector, rank:1}]
degraded: ausente (as duas pernas íntegras)
```

**Status: `passed`.** E a evidência é mais forte que a presença do campo: ele **discrimina em
dados reais**. `triagem-chamado` — *"classifica e prioriza chamados de suporte"* — não tem
sobreposição léxica com a consulta, e a perna `keyword` **não** o trouxe. A atribuição diz
exatamente isso. `cambio-real` casou nas duas, com rank diferente em cada.

Isto é o que um teste unitário não prova: que a atribuição corresponde ao que as duas buscas de
fato fizeram contra um banco com dados.

## Critério 2 — o que NÃO foi validado, e por quê

**`matched` não foi exercitado no `app-dev`.** Medido, não presumido:

| Rota tentada | Resultado |
|---|---|
| `GET /v1/skills:retrieve` (borda) | `401` — exige chave de API do serviço, que não tenho |
| `GET /v1/dashboard/skills:retrieve` | `404` — rota não existe |
| `GET /v1/dashboard/skills/retrieve` | `401` |

**O BFF do dashboard não proxia o `:retrieve`.** Isso não é falha desta entrega — é precisamente
a lacuna que a auditoria de UX mediu (*a descoberta não tem superfície*) e que o plano das telas
fecha. Registrado como caveat, não como sucesso.

Por isso o verdict é `ACCEPTED_WITH_CAVEATS` e não `ACCEPTED`: um dos dois critérios foi provado
contra o artefato liberado, e não contra a instância no ar.

## Defeitos observados no caminho

1. **`401` do dashboard instrui a rodar comando de CLI.** `{"code":"AUTH_REQUIRED","message":"Not
   authenticated. Run: theo login"}` — devolvido a um navegador. É o defeito que o `CLAUDE.md`
   deste repo já nomeia ("mensagem de erro escrita para o terminal"). Não filei issue: já está
   documentado como classe conhecida; vale corrigir quando as telas forem tocadas.
2. **O rodapé diz "10 operational" enquanto telas de Memory dizem "not reachable".** Duas
   checagens diferentes, e quem lê o rodapé não sabe disso. Registrado na auditoria
   `2026-08-04-skills-vs-memory-padrao-medido.md`.
