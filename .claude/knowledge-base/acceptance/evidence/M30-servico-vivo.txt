# M30 — os cinco critérios contra o SERVIÇO VIVO, construído do build 0.2.0 (2026-08-03)
# postgres real (ankane/pgvector:v0.5.1 :15999), migrations aplicadas, node dist/server.js

$ curl /v1/health                                        -> {"status":"ok"}

# AC1 — mesmo `code` nas duas rotas, do MESMO ingestPayload
$ POST /v1/skills:validate  {"zippedFilesystem":""}      -> {"error":"invalid_zip"}
$ POST /v1/skills           {"skill_id":"m30-x", ...}    -> {"error":"invalid_zip"}
  ^ idênticos. É a comparação que o teste de contrato NÃO conseguia fazer sem banco.

# AC2 — zero efeito colateral, por CONTAGEM
$ GET /v1/skills  -> 0 skills
$ POST /v1/skills:validate  (payload VÁLIDO) × 3
$ GET /v1/skills  -> 0 skills
  ^ três validações com payload que passa, e nada foi criado.

# AC3 — SKILL.md avulso, sem ZIP
$ POST /v1/skills:validate  {"skillMd":"---\nname: m30-aceite\n..."}
  {"ok":true,"name":"m30-aceite","description":"skill de aceitacao do M30","execution":"remote"}
  ^ os campos foram EXTRAÍDOS do arquivo avulso pelo mesmo pipeline.

# AC4 — o erro diz ONDE
$ POST /v1/skills:validate  {"skillMd":"---\ndescription: sem nome\n---..."}
  {"error":"schema_invalid","message":"missing required field: name","field":"name"}
  ^ `error` PRESERVADO (compat) + `message` + `field`. Sem `line` porque o campo ausente
    não tem posição no arquivo — inventá-la mandaria o editor pintar a linha errada.

# AC5 — exige autenticação
  Primeira execução: 200 sem bearer. Causa MEDIDA no log do serviço:
  {"msg":"auth DESLIGADA (THEOSKILL_AUTH_REQUIRED != true) — o serviço não deve ser exposto assim"}
  Não era defeito do AC5: era a instância local com auth desligada por configuração.

$ THEOSKILL_AUTH_REQUIRED=true node dist/server.js   -> {"auth_required":true}
$ POST /v1/skills:validate  (payload VÁLIDO, SEM bearer)  -> 401
  ^ com auth ligada, a rota exige credencial. Payload válido de propósito: um payload
    inválido daria 400 e não distinguiria "recusou por auth" de "recusou por conteúdo".
